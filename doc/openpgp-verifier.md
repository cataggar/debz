# OpenPGP verification boundary

`debz.openpgp_verifier` is an in-process, dependency-free verification boundary
for Debian-family repository metadata. It never invokes a command, performs
network discovery, reads a home directory, or consults an ambient keyring.
Callers provide the exact signed bytes, binary signature packets, and every
binary public keyring as bytes or an explicit path.

## Backend and license decision

RNP 0.18.1 (tag commit `aad1892e4d8423398a0b973bd0a7e4544c359afc`)
was evaluated. RNP is BSD-2-Clause/Apache-2.0 and its documented production
closure uses Botan or OpenSSL, plus zlib, bzip2, json-c, and bundled or system
sexpp. Those components are permissively licensed. However, RNP's upstream
CMake build has a network fallback for its version module and its complete
C/C++ dependency closure is not presently pinned or built by this Zig graph.
Adding it would therefore fail debz's deterministic-Zig-build requirement.
Sequoia was excluded because its production library is LGPL-2.0-or-later.

The selected implementation is a narrow debz-owned parser and verifier using
only Zig 0.16.0 standard-library SHA, RSA, and Ed25519 primitives. Backend types
remain private. This adds no production dependency or license obligation.

## Supported profile

The supported profile is intentionally exact:

- OpenPGP v4 public keys and signatures.
- RSA public-key algorithms 1 (`RSA Encrypt or Sign`) and 3 (`RSA Sign-Only`).
- RSA moduli of 2048, 3072, or 4096 bits. Other sizes fail explicitly.
- Legacy OpenPGP EdDSA algorithm 22 with the Ed25519 OID and 32-byte key.
- SHA-256 (algorithm 8) and SHA-512 (algorithm 10).
- Binary-document signatures (type 0) and canonical-text signatures (type 1).
- v4 primary-key fingerprints, signing-subkey fingerprints, issuer fingerprint
  and key-ID hints, self-certifications, direct-key signatures, subkey binding,
  signing-subkey cross-certification, key expiration, key flags,
  primary/subkey revocation, and mandatory authenticated signature
  creation/expiration.

As checked on 2026-08-15, Debian 13 stable's official `InRelease` contains two
RSA/SHA-256 signatures and one algorithm-22 Ed25519/SHA-256 signature. Its
archive and security keys are RSA-4096, while its per-release stable key is
Ed25519. Ubuntu 24.04's official `InRelease` contains RSA-4096/SHA-512. This
profile deliberately does not claim DSA, ECDSA, other curves, OpenPGP v5/v6,
or any other hash algorithm. Such signatures receive an explicit unsupported
result.

The check used the official Debian key page and keys
(`ftp-master.debian.org/keys.html`), Debian stable `Release`/`Release.gpg`, the
official Ubuntu archive keyring, and Ubuntu Noble `InRelease`. The Debian
profile was also exercised end-to-end locally: all three current detached
`Release.gpg` signatures verified against the three explicitly supplied Debian
13 keys. No downloaded artifact is part of the committed test suite.

Signature issuer subpackets only narrow candidate selection. A result is never
accepted from an issuer hint: the selected key must verify the signature, its
binding and relevant self-signatures must verify, and the primary fingerprint
must pass caller policy. Declared revocation packets that cannot be validated
within the narrow profile conservatively revoke their attached key rather than
allowing a false success.

## Limits and outcome

`Limits` bounds signed bytes, combined keyring bytes, signature bytes, packet
size/count, key count, and subpacket size/count. Partial-body packet lengths,
non-canonical MPIs, malformed lengths, and unknown critical subpackets are
rejected. ASCII armor decoding is intentionally outside this boundary.

`verify` returns an `Outcome`: `.accepted` only when at least one signature is
cryptographically valid and policy-accepted, otherwise `.rejected`. Both carry
deterministically ordered per-signature results. There is no fallback success.

`inspectKeyring` applies the same bounded binary parser without verifying a
document and returns sorted supported v4 primary-key fingerprints. This
preflight is intentionally stricter than verification of a mixed keyring:
unsupported public or secret key material, unsupported RSA modulus sizes,
unusable RSA public parameters, malformed packets, an empty supported-key set,
and ASCII armor all fail explicitly.

The checked-in fixtures are generated from non-secret RSA and Ed25519 test keys by
`tools/generate-openpgp-fixtures.py`; normal builds and tests use only the
generated bytes and do not require Python or its cryptography package. Optional
regeneration uses the exact development pin in
`tools/requirements-openpgp-fixtures.txt`.
